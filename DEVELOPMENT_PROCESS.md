# Development Process

Этот документ описывает рабочий процесс разработки для проекта Fifteen Game.

Мы используем его как основной регламент для любой новой фичи, исправления бага или изменения существующей логики.

## Главный принцип

Наша цель не просто написать код.
Наша цель - довести изменение до состояния, в котором его безопасно принимать в основную ветку без лишнего ручного труда в будущем.

## Базовые правила

- Предпочитать простые решения.
- Не усложнять архитектуру без необходимости.
- Не делать крупный рефакторинг ради стиля.
- Менять только минимально необходимое количество файлов и логики.
- Сохранять существующие соглашения проекта, если нет объективной причины их менять.
- Не ухудшать читаемость кода.

## Жизненный цикл любой задачи

Каждая задача проходит одинаковые этапы.

### 1. Анализ перед реализацией

Перед написанием кода нужно:

- изучить текущую реализацию;
- определить, какие файлы и компоненты будут затронуты;
- оценить влияние изменения на существующую функциональность;
- коротко сформулировать план реализации;
- явно указать, какие существующие сценарии потенциально могут сломаться.

Если изменение рискованное, нужно отдельно отметить:

- что уже покрыто тестами;
- каких тестов не хватает;
- что придется проверить руками.

### 2. Реализация

Во время реализации нужно:

- вносить минимально необходимое изменение;
- избегать дублирования;
- по возможности не менять публичные интерфейсы без необходимости;
- не смешивать в одном изменении несколько разных задач;
- сохранять совместимость существующих пользовательских сценариев.

### 3. Обновление регрессионного контура

Каждое изменение должно сопровождаться оценкой тестового покрытия.

После реализации нужно решить:

- нужны ли новые unit-тесты;
- нужны ли новые integration-тесты;
- нужно ли расширить Firebase Emulator coverage;
- нужно ли расширить Playwright smoke;
- нужны ли новые functional E2E-сценарии;
- нужно ли обновить manual smoke checklist.

Мы не добавляем тесты ради количества.
Каждый новый тест должен защищать от конкретной вероятной регрессии.

### 4. Локальная проверка

Перед завершением задачи необходимо убедиться, что:

- новые тесты проходят;
- старые тесты не сломаны;
- изменение соответствует исходной задаче;
- критичные существующие сценарии не деградировали.

Минимальный набор проверки зависит от характера изменения, но обычно включает:

```bash
npm test
npm run test:integration
npm run test:e2e
```

Если изменение релизное или затрагивает опубликованную версию, дополнительно:

```bash
npm run test:e2e:prod
```

### 5. Что проверяем руками

Мы не прогоняем весь продукт руками после каждой фичи.

Ручная проверка нужна в первую очередь для:

- самой новой фичи;
- нестандартных UX-сценариев;
- визуальных дефектов;
- поведения, которое еще не автоматизировано;
- короткого release smoke перед публичным релизом.

Если сценарий стабилен и регулярно нужен для проверки, его надо переводить в автоматизированные тесты.

## Обязательный формат завершения работы по фиче

После реализации я должен явно сообщать:

### 1. Что было изменено

- какая функциональность добавлена или исправлена;
- какие файлы были затронуты;
- зачем потребовалось изменение.

### 2. Какие сценарии были под риском

- какие существующие части системы потенциально могли сломаться;
- что из этого уже было покрыто тестами;
- какие новые тесты добавлены для защиты от регрессии.

### 3. Что проверено

- какие unit-тесты запускались;
- какие integration-тесты запускались;
- какие Playwright-тесты запускались;
- что было проверено руками;
- что осталось риском, если такой риск есть.

## Правило экономии ручного труда

После каждой новой фичи нужно стремиться к следующему:

- новую фичу проверить руками сейчас;
- повторяемую регрессию перевести в автоматические тесты;
- в будущем не возвращаться к полной ручной перепроверке старого поведения.

Иными словами:

- руками проверяем новое;
- автотестами защищаем стабильное;
- релизный ручной smoke оставляем коротким и точечным.

## Работа с багфиксами

Если найден реальный пользовательский баг:

- сначала оценить риск для данных и пользовательских сценариев;
- исправить минимальным изменением;
- обязательно добавить тест, если баг может повториться в будущем;
- отдельно проверить, не затрагивает ли фикс существующую логику.

## Работа с внешним review

Для всех нетривиальных изменений рекомендуется проводить независимое code review.

### Уровни review

Мы используем два уровня review: легкий и полный.

### Легкий review

Легкий review подходит для:

- небольших багфиксов;
- маленьких локальных фич;
- точечных тестовых доработок;
- изменений с низким риском и маленьким diff.

Формат легкого review:

1. Отдельная ветка.
2. Один логичный коммит или небольшая серия связанных коммитов.
3. Compare link или diff.
4. Короткое описание:
   что изменено, какой риск, какие тесты пройдены.

Цель легкого review - быстро понять, корректен ли фикс и нет ли очевидной регрессии.

### Полный review

Полный review подходит для:

- миграций;
- изменений backend-логики;
- крупных фич;
- risky refactor;
- изменений, которые влияют на данные, релизный процесс или несколько слоев системы.

Формат полного review:

1. Отдельная ветка.
2. Логично разбитые коммиты.
3. Compare link или Pull Request.
4. PR package или расширенное описание изменений.
5. Явное перечисление рисков.
6. Явное перечисление тестового покрытия.

Цель полного review - не только проверить код, но и проверить безопасность внедрения изменения.

### Как выбирать уровень review

После каждого коммита или логического блока изменений я обязан явно предложить:

- нужен ли легкий review;
- или нужен полный review;
- и кратко объяснить почему.

По умолчанию:

- для маленьких фиксов и узких изменений предлагается легкий review;
- для нетривиальных изменений предлагается полный review.

### Рекомендуемый процесс review

1. Реализовать изменение.
2. Пройти локальные тесты.
3. Сделать commit только после зеленого локального контура.
4. Запушить изменение в отдельную рабочую ветку, а не в `main`.
5. Подготовить краткое описание изменений.
6. Выбрать подходящий уровень review: легкий или полный.
7. Передать diff, compare link или Pull Request на внешнее review.
8. Обработать замечания.
9. При необходимости внести исправления, снова пройти тесты, сделать commit и push в ту же ветку.
10. Только после этого считать изменение готовым к merge.

### Обязательный branch -> review -> merge flow

Для всех изменений кода и тестов мы используем следующий основной процесс:

1. Codex реализует задачу.
2. Codex добавляет или обновляет тесты.
3. Codex запускает все необходимые тесты.
4. Если все зеленое, Codex делает commit.
5. Codex делает push в рабочую ветку вида `feature/...`, `fix/...`, `test/...` или другую осмысленную ветку.
6. Создается Pull Request или используется compare diff этой ветки.
7. Claude ревьюит именно Pull Request, compare diff или diff ветки, а не локальное описание на словах.
8. Codex анализирует замечания в формате `Accepted`, `Rejected` или `Partially Accepted`.
9. Если замечания приняты полностью или частично, Codex вносит исправления, снова прогоняет нужные тесты, делает commit и push в ту же ветку.
10. При необходимости Claude повторно проверяет обновленный Pull Request.
11. Только после этого выполняется merge в `main`.

Из этого правила есть только одно упрощение:

- для маленьких `docs-only` изменений можно использовать тот же процесс в более легком режиме review;
- для изменений кода, тестов, Firebase-логики и пользовательских сценариев branch -> review -> merge flow считается основным и обязательным.

Если используется внешнее review от другой модели или другого инструмента:

- не принимать замечания автоматически;
- для каждого замечания явно определить статус:
  `Accepted`, `Rejected` или `Partially Accepted`;
- кратко объяснить причину решения;
- если замечание принято, внести минимально необходимое изменение;
- при необходимости обновить тесты.

## Критерий завершения задачи

Задача считается завершенной только если:

- функциональность реализована или баг исправлен;
- нужные тесты добавлены или обновлены;
- релевантный регрессионный контур пройден;
- известные риски явно обозначены;
- изменение готово к дальнейшему review или к безопасному продолжению работы.

## Как мы применяем этот документ

Этот документ используется как постоянный стандарт работы.

Для каждой новой фичи я должен:

- сначала оценить влияние на существующую систему;
- предложить минимально достаточный набор автоматизации;
- после реализации явно сказать, что теперь можно больше не проверять руками;
- поддерживать регрессионный контур в актуальном состоянии;
- после каждого коммита предложить подходящий уровень review: легкий или полный.

## Главный принцип развития проекта

Главная цель проекта - не максимальное количество кода.

Главная цель - сохранять возможность безопасно развивать проект.

Если существует выбор между:

- более сложной реализацией;
- более простым решением,

предпочтение отдается более простому,
если оно не ухудшает качество продукта.

Если существует выбор между:

- написанием нового ручного сценария проверки;
- автоматизацией повторяющейся проверки,

предпочтение отдается автоматизации,
если ее стоимость разумна.
